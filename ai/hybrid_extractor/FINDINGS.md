# 調査結果のまとめ（hybrid_extractor、2026-11-08〜11-25）

ルールベース＋自作AIの PDF 抽出器で、**何をしたら精度が上がり、どの手法が効いたか**をまとめる。
アルゴリズムの説明は [AI.md](AI.md)、抽出器の仕組みは [README.md](README.md)、入力の制約は [../CONSTRAINTS.md](../CONSTRAINTS.md)。

## 結論

1. **AI の専門家は、ルールよりはっきり良い。** 区切り 0.919 → 0.986、ラベル 0.821 → 0.982（テスト用データ）。
   作り方の違う文書・見たことのない中身でも、AI はルールより上
2. **一番効いたのは「モデル」より「手がかり（特徴）とデータ」。** 書体によらない手がかりへの置き換え、近道を潰すデータ、
   段落の専門家の追加、データの不具合の修正が、どれもモデルを変えるより大きく効いた
3. **ハイパーパラメータは、ほとんど効かない。** ラベルはどの設定でも ±0.001。区切りも、良い設定にして +0.003 くらい
4. **AI は学習の材料（言い回し・数式の形）をある程度覚えている。** 見たことのない中身で、検出F1 が 2〜4 ポイント下がる。
   見た目（書体・文書クラス）の変化には強い
5. **差が 0.005 以下のときは、ぶれ（乱数の種・60文書）と区別できない。** 種を変えて何回か測る必要がある

## 1. 精度が上がったもの

| 施策 | 何を変えたか | 結果 |
|---|---|---|
| 区切りの専門家を AI に | 2行が同じブロックかを、31個の手がかりの MLP で判定 | テストの正解率 0.919 → **0.986**（ルールの「割りすぎ」が消えた） |
| ラベルの専門家を AI に | ラベルごとの MLP 8人＋オペレータ（一番自信のある答え） | オペレータで決めた正解率 0.821 → **0.982** |
| **段落の専門家を足す** | 「誰も手を挙げなければ段落」をやめ、段落にも専門家を付けた | 0.959 → **0.979**（適合率の低い専門家に段落が負けていた） |
| **近道（ショートカット）を潰すデータ** | 「表2に示すように…」で始まる段落を学習データに足した | 「表1は…」で始まる段落のキャプションの自信 0.97 → **0.06** |
| 文中の数式のしきい値を検証用データで選ぶ | 0.5 → 0.9（pos_weight で自信過剰になるため） | 数式のまとまりの F1（検証）0.920 → **0.944** |
| 範囲の後処理（間が空白・演算子ならつなぐ） | 1文字ずつの確率から範囲を作るとき | 入れ忘れたとき 0.767 → 入れて **0.888**（見つける F1） |
| **書体によらない手がかり**（許可リスト段階1） | 等幅は送り幅、数式は短い斜体の並び、行の間隔はベースライン | ルールの検出F1 0.858 → **0.907**、コード 0.54 → **0.96**、数式 0.70 → **0.93** |
| 字下げは文字の並ぶ間隔で数える | listings は文字を枠の幅より広い間隔で並べる | コードの字下げ 0.705 → **0.972** |
| 書体を混ぜた学習データで学習し直す | doc_gen に 8 つの欧文・T1・等幅・和文の書体 | AI の検出F1 0.970 → **0.981**、ラベル 0.976 → **0.985** |
| 数式を読む係の書体対応 | 大きいかっこの書体（LMMathExtension）、太字の印、小さいかっこの \binom | 読む完全一致 0.967 → **0.984**（lmodern 0.940 → 0.991） |
| **データの不具合を直す** | newtxtext で PDF から図が黙って消えていた（graphicx のドライバ） | 図のある文書のキャプションが正しく付くように |
| 蒸留（文中の数式） | 同じ形のモデル3つの平均を先生にして生徒を学習 | 1文字ずつの F1 0.9495（先生1人の平均）→ **0.956**（1人分の速さのまま） |

## 2. 効かなかった・効き目が限られたもの

| 試したこと | 結果 | 理由・教訓 |
|---|---|---|
| 蒸留で**速く**する | 効き目は小さい | モデルの計算は 1ページ 0.04秒で、残り（特徴づくり・PDF の読み込み）が大半 |
| 蒸留の**数式のまとまり**の F1 | 0.9504〜0.9538（先生）→ 0.9538（生徒） | 先生どうしのぶれと同じくらいで、効いたとは言い切れない |
| 書体の名前の一覧を増やす | 足りない | PDF の等幅の印は TeX の書体に付かない。数式の文字が本文の斜体と同じ書体になる（mathptmx・mathpazo） |
| ハイパーパラメータ（ラベル） | どの設定も ±0.001 | 手がかりとデータで決まっている |
| 本物のレポート（制約の外の書き方）での評価 | 検出F1 ルール 0.247・AI 0.387 | minted・T1 fontenc・LuaLaTeX など制約の外。比較には使わないと決めた |

## 3. ハイパーパラメータの比較

いつもの設定（隠れ層 64、学習率 1e-3、バッチ 256、最大 60 エポック＋早期終了 6回、pos_weight あり）から1つだけ変え、
乱数の種 3つの平均（± は標準偏差）。良い設定は検証用データで選ぶ（[sweep.py](sweep.py)、結果は data/sweep_*.json）。

### 区切りの専門家（MLP、検証の正解率）

|---|---|---|---|
| **いつもの設定** | 0.9857 ±0.0019 | 25 | 9秒 |
| 最大エポック 1 / 3 / 5 / 10 / 20 | 0.9500 / 0.9699 / 0.9745 / 0.9812 / 0.9852 | | |
| **早期終了なし（60エポック全部）** | **0.9883** ±0.0021 | 60 | 20秒 |
| 隠れ層 8 / 16 / 32 | 0.9820 / 0.9853 / 0.9860 | | |
| **隠れ層 128 / 256** | **0.9880 / 0.9885** | 27 / 19 | 13 / 14秒 |
| 学習率 1e-4 / 3e-4 / 3e-3 / 1e-2 | 0.9789 / 0.9851 / 0.9853 / 0.9858 | | |
| バッチ 32 / 128 / 1024 / 4096 | 0.9841 / 0.9865 / 0.9855 / 0.9787 | | 28 / 15 / 8 / 7秒 |
| pos_weight なし | 0.9862 | | |

- **エポック:** 20 エポックまでは伸び続ける。早期終了は平均 25 エポックで止まっていたが、止めずに 60 回すと +0.003。
  早期終了は「検証の損失」で判定していて、損失が横ばいでも正解率はまだ伸びていた（判定に使う物差しと、見たい物差しがずれていた）
- **隠れ層:** 大きいほど少し良い（8 → 256 で +0.007）。128 以上で頭打ち
- **学習率:** 1e-4 は 60 エポックでは学習しきれない。3e-4〜1e-2 はほぼ同じ（Adam は学習率に鈍い）
- **バッチ:** 4096 は更新の回数が少なすぎて学習しきれない（フルバッチに近いほど遅い）。32 は時間が3倍で、少し悪い
- **pos_weight:** 区切りは「続き」と「区切り」がほぼ半々（49%）なので、あってもなくても同じ
- 一番良い設定の差は +0.003 で、ぶれ（±0.002）の少し上。「隠れ層 128 ＋ 早期終了なし」にしてもよいが、大きくは変わらない

## 4. 見たことのない見た目・中身への強さ

（詳しくは [AI.md](AI.md) の 7.7。評価は60文書ずつ、学習と別の種）

| 何を変えたか | AI の検出F1 / ラベル | ルールの検出F1 / ラベル |
|---|---|---|
| 学習と同じ作り（書体を混ぜた文書） | 0.981 / 0.985 | 0.907 / 0.911 |
| 書体（Times の仲間）を学習に見せない | 0.982 / 0.985（落ちない） | |
| 文書クラス（bxjsarticle）を学習に見せない | 0.976 / 0.983（落ちない） | |
| 箇条書きの記号（★・―・▷）を学習に見せない | 0.975 / 0.991、**箇条書き F1 0.88 → 0.82** | |
| 別の材料（単語・見出し・数式の部品・コード） | 0.958 / 0.970 | 0.880 / 0.906 |
| 本物の文（青空文庫・Gutenberg）と数式（im2latex） | 0.939 / 0.964 | 0.825 / 0.930 |

- 書体・文書クラスは、書体によらない手がかりのおかげで、見たことがなくても落ちない
- 箇条書きは、AI が記号そのものを覚えていた
- 中身の変化の方が効く。段落（0.94 → 0.82）・箇条書き（0.85 → 0.68）・数式（0.97 → 0.89）が下がる。ルールは言い回しを見ないので、ラベルは下がらない
- 本物の数式（論文の長い数式）では、文中の数式を見つける F1 がルール 0.891 → 0.760、AI 0.908 → 0.807

## 4.5 数式を外して採点し、学習の材料を増やした（案 B、2026-11-25）

数式は担当外なので、全体の点数から数式ブロックを外して採点した（正解の数式ブロックと、それに重なる予測を数えない。
数式の点数は別に出す。generalization.py）。評価の中身は数式だけ今の材料のまま（alt_text・real_text）。
学習の材料は、本物の文は評価だけに残し、手で用意した材料（単語・見出し・キャプションの語・コード・文の形）を増やした（wide。alt と1語も重ならない）。
ハイパーパラメータはいつものまま（材料の効き目だけを見る）。文中の数式の専門家は学習し直していない。

| データ（数式を除いて採点） | ルール 検出F1 / ラベル | 今の AI | AI（wide で学習） |
|---|---|---|---|
| 学習と同じ材料（hybrid_fonts） | 0.907 / 0.906 | 0.982 / **0.984** | 0.982 / 0.973 |
| 別の材料（alt_text） | 0.892 / 0.910 | 0.958 / **0.975** | **0.969** / 0.968 |
| 本物の文（real_text） | 0.854 / 0.932 | 0.981 / 0.956 | **0.989 / 0.960** |

- **前回の「中身で検出F1 が 4 ポイント下がる」の大半は、数式だった。** 数式を今の材料のままにして外して採点すると、
  本物の文でも AI の検出F1 は 0.982 → 0.981 で下がらない。下がるのはラベル（0.984 → 0.956。段落 0.94 → 0.90、箇条書き 0.85 → 0.76）
- **材料を増やすと、見たことのない中身での検出（区切り）が良くなる**（+0.011 / +0.008）
- **ラベルは、箇条書きだけ下がった**（学習と同じ材料で箇条書き F1 0.85 → 0.74、ラベル 0.984 → 0.973）。間違いのほとんどは、
  description の箇条書き（太字の見出し語＋説明）を段落と答えたもの（10件 → 21件）。学習データには、そっくりな「太字の語で始まる段落」もある。
  今の AI は、2つを見た目ではなく**見出し語の単語そのもの**で見分けていた。材料を増やして見出し語が増えたら、その近道が使えなくなった
- 別の材料のコード（C・JavaScript・シェル）は、ルールも AI もコードの F1 が 0.85 くらい。コードの見分けにも、コードの中身の覚えがありそう
- どれも種1つ・60文書なので、±0.005 くらいはぶれの範囲

**次:** description の箇条書きと「太字の語で始まる段落」を、見た目で見分ける手がかりを足す（見出し語の後ろのぶら下げの字下げ、
同じ形の行が縦に続くこと、項目の間のすき間）。そのうえで wide で学習し直す。

## 4.6 箇条書きを見た目で見分ける手がかり ＋ 材料を増やす（2026-11-28）

ラベルの専門家の手がかりに、ブロックの**行ごとの記録**（左端・太字の語で始まるか・記号や番号で始まるか）から作る5つを足した（52 → 57個）:
太字で始まる行の割合・**太字で始まる行の数**・ぶら下げの項目の数・同じ位置にそろった記号の数・本文の左端からの字下げ（`features.list_layout`）。
description の箇条書きは項目ごとに太字で始まる行があるが、「太字の語で始まる段落」は最初の1行だけ、というのが一番効く違い
（jsarticle の description はぶら下げにならないので、字下げでは見分けられない）。前の重みには先頭の52個だけを渡すので、そのまま動く。

材料の効き目と手がかりの効き目を分けるため、2×2 で比べた（数式を除いて採点、60文書ずつ、種1つ）。

| データ | 今の AI | 手がかりだけ（lay） | 材料だけ（wide） | **両方（wide_lay）** |
|---|---|---|---|---|
| 学習と同じ材料: 検出F1 / ラベル | 0.982 / 0.984 | 0.982 / **0.988** | 0.982 / 0.973 | 0.982 / 0.985 |
| 別の材料（alt_text）: 検出F1 / ラベル | 0.958 / 0.975 | 0.958 / 0.982 | 0.967 / 0.968 | **0.969 / 0.983** |
| 本物の文（real_text）: 検出F1 / ラベル | 0.981 / 0.956 | 0.979 / 0.961 | **0.989** / 0.960 | **0.989 / 0.982** |
| 本物の文: 箇条書き F1 / 段落 F1 | 0.76 / 0.90 | 0.77 / 0.90 | 0.76 / 0.92 | **0.89 / 0.96** |

- **両方そろって、はじめて大きく効いた。** 本物の文でラベル 0.956 → 0.982、箇条書き 0.76 → 0.89、段落 0.90 → 0.96。
  見たことのない中身での「学習と同じ材料」との差（ラベル）が 0.028 → 0.003 に縮んだ
- **片方だけでは効かない理由:** 材料だけ増やすと、単語の近道が使えなくなるのに、代わりの手がかりが無い（箇条書きが下がる）。
  手がかりだけ足しても、学習データの単語の近道の方が楽なので、AI は新しい手がかりをあまり使わない（見たことのない中身では少ししか上がらない）。
  **近道を潰す（材料を増やす）ことと、本当の手がかりを渡すことを、一緒にやる必要がある**
- 区切り（検出F1）は材料を増やした効果（+0.008〜0.011）がそのまま残った
- ルールとの差: 本物の文で、ラベル正解率 ルール 0.932 → AI 0.982（前の AI は 0.956 で、差が縮んでいた）

## 4.7 種を変えて確かめ、いつもの重みにした（2026-11-28）

今の AI と wide_lay を、種を 3つずつ変えて学習し、平均 ± 標準偏差で比べた（数式を除いて採点）。

| データ | 今の AI 検出F1 / ラベル | wide_lay 検出F1 / ラベル | 箇条書き F1 | 段落 F1 |
|---|---|---|---|---|
| 学習と同じ材料 | 0.978±0.005 / 0.983±0.002 | **0.982±0.000 / 0.985±0.000** | 0.83 → 0.85 | 0.94 → 0.94 |
| 別の材料（alt_text） | 0.958±0.003 / 0.976±0.001 | **0.971±0.002 / 0.981±0.002** | 0.74 → 0.82 | 0.92 → 0.94 |
| 本物の文（real_text） | 0.979±0.002 / 0.956±0.004 | **0.989±0.001 / 0.982±0.001** | 0.74 → **0.89** | 0.90 → **0.96** |

- 3つのデータ全部で、ぶれの範囲を大きく超えて良い（本物の文のラベル +0.026 は、ぶれ ±0.004 の6倍以上）
- **種によるぶれも小さくなった**（学習と同じ材料の検出F1 ±0.005 → ±0.000、箇条書き ±0.034 → ±0.017）。
  近道（単語）に頼るモデルは、どの近道を覚えるかが種で変わるので、ぶれが大きい
- 学習のときのテスト（同じ材料）ではぶれは ±0.001 でも、評価サイトの形の 60 文書では、箇条書き F1 が種だけで 0.06 動いた。
  箇条書きのような数の少ないラベルは、種を変えて測らないと判断できない
- → **wide_lay を、いつもの重み（checkpoints/ 直下の boundary.pt・labels/）にした。** 前の重みは checkpoints/_v2/。
  文中の数式の専門家は変えていない（数式は担当外）。学習し直すときは、学習データを `--content wide` で作る

## 5. 実験のやり方で分かったこと

- **乱数の種だけで F1 が 0.004〜0.006 ぶれる。** 同じ形・同じデータでも。0.005 くらいの差は、種を変えて何回か測らないと言えない
- **学習と評価を同じ作り方で作ると AI に有利。** 評価用データは作り方を変える（#50）か、見た目・中身を学習から抜いて測る
- **直す前と後は、同じデータで測る。** データを作り直したら、直す前のコードも git worktree で測り直した（書体の作業で、データの不具合を直したとき）
- **点数が急に下がったら、まずエラーを見る。** 数式を読む係の例外で 10 文書が丸ごと 0 点になっていたことがある
- **データの不具合は、点数だけでは気づけない。** 「キャプションなのに段落」を1つずつ見て、PDF から図が消えていたと分かった
- **物差しと見たいものをそろえる。** 早期終了の判定（検証の損失）と、見たい成績（正解率）がずれていて、学習を早く止めすぎていた
- **数式の精度は担当外なので、全体の点数から分けて見る。** 外して採点したら、「中身で大きく下がる」の大半が数式だったと分かった
- **材料を増やして下がったら、近道が表に出たと疑う。** 箇条書きが下がったのは、AI が見出し語の単語を覚えて当てていたため
- **近道を潰すことと、本当の手がかりを渡すことは、一緒にやる。** 片方だけでは効かず、両方で本物の文の箇条書き 0.76 → 0.89

## 6. 今後の指針

**基本: 近道を潰して、本当の手がかりを渡す。** 一番大きく効いたのは、いつも次の組み合わせだった:
① 間違いを1つずつ見て、AI が使っている近道（単語・記号・書体の名前）を見つける →
② データを変えて近道を使えなくする（材料を増やす、見た目をばらつかせる）→ ③ 見た目の本当の手がかりを渡す
（送り幅、ベースライン、行ごとの太字・記号のそろい方）。片方だけでは効かない。弱いラベルから順に回す。

1. **今の弱い所を、この手順で直す**
   - 見たことのない言語のコード（C・JavaScript・シェル）: コード F1 0.85（ルールも同じ）。等幅の手がかりはあるのに外れる理由を見る
   - 見出しのレベル: AI 0.93〜0.94（ルール 0.96）。レベルの決め方はルールのままなので、そこを見直す
   - 記号の箇条書きの、知らない記号（前回 0.88 → 0.82）: 今回の「そろった記号」の手がかりで戻るかを確かめる
   - 本物の文でのコードの字下げ 0.90
2. **許可リストの段階2・3に広げる**（文書クラス・エンジン・組版 → 見た目を変えるパッケージ）。
   どの段階でも、先に「学習から抜いた見た目」で測ってから直す。名前の一覧を足すのではなく、見た目によらない手がかりにする
3. **物差しを本番に近づける**: #50 の評価用データ（作り方が違う）、許可リストの中の本物の文書（エディタで書いた文書など）。
   種3つの平均とぶれ、数式を外した点数をメインにする。差が 0.005 以下なら効いたと言わない
4. **モデルの側（優先度は低い）**: ハイパーパラメータはほとんど効かない（区切りで +0.003 くらい）。
   ページのブロックの並び全体を見るモデル（ブロック単位の Transformer）にすると、箇条書きの続きや見出しのレベルの順番のつじつまが取れるが、
   大きな作り直しになる。蒸留・アンサンブルは小さく効く（最後に少し足したいとき）
5. **やらない方がよいこと**: 書体の名前や記号の一覧を足していく／学習と同じ作り方のデータだけで点数を上げる／
   評価用の材料（本物の文・alt）を学習に混ぜる
